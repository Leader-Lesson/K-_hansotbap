# 백엔드 핵심 기능 비교 실험 설계 (결과 보고서용)

> 프론트 없이 백엔드 함수·API만으로 잰다. 모든 입력은 합성 데이터(`app/samples/`)다.
> 숫자는 **직접 돌려서 나온 값만** 보고서에 쓴다. 아래 표의 빈칸(○)은 측정 전이다.

## 지금까지 측정된 값 (2026-11-09, LLM 없이 잴 수 있는 것)

LLM 조건(①②④⑥)은 아직 못 쟀다. 레포 루트 `.env`의 `ANTHROPIC_API_KEY`가 비어 있다(키는 각자 넣는다).

### 추출 (F1) — 파싱 + 규칙

| 표본 | 칸 정확도 | 작업 완전 일치 | 못 읽은 파일 | 건당 시간 | 반복 일치(3회) |
|---|---|---|---|---|---|
| 기본 5건 (작업 13 · 칸 103) | **99.0%** (102/103) | 92.3% (12/13) | 0 | 0.17초 | 100% |
| ⑤ 통일 양식 5건 (`samples/uniform/`) | **99.0%** (102/103) | 92.3% (12/13) | 0 | 0.02초 | 100% |
| 변형 20건 (`samples/variants/`, 칸 412) | **71.6%** (295/412) | 57.7% (30/52) | 5 | 0.28초 | 100% |

변형에서 틀린 117칸의 원인:
- **문장형 5건(작업 13개)을 못 읽음** — 표가 없으면 규칙 경로는 0. LLM 조건이 이걸 얼마나 살리는지가 실험의 핵심
- **두 자리 연도(`27.1.15`) 날짜 11칸** — 규칙이 못 알아봄 (규칙 보강 후보)
- **기준 일정 ID 3칸** — 비계 P30을 두 작업이 나눠 쓰는 알려진 한계. 통일 양식에도 같은 1칸이 남는다: 양식에 「기준 일정 ID」 칸이 있어도 추출기가 그 칸을 읽지 않고 작업명으로 찾기 때문 (규칙 보강 후보 — 고치면 통일 양식 100%)
- 나머지 표 변형(머리글 낱말·열 순서·병합 셀·업체명 위치·한글 날짜·기간 한 칸·시간대 칸)은 모두 100%

### 충돌 판정 (F2) — `samples/eval_conflicts.py`

| 입력 | 재현율(정답 충돌 6건) | 규칙까지 모두 맞음 | 판정 시간 |
|---|---|---|---|
| 정답 작업 그대로 | **100%** (6/6) | 66.7% (4/6) | 기준 37개 21~26ms · +계획서 5건 25~42ms |
| 파싱 + 규칙 추출 결과 | **100%** (6/6) | 66.7% (4/6) | 같음 |

- 「규칙까지 모두」: S2(기계J)는 R16만, 같은 시간·구역(비계N)은 R17만 나옴 — 정답셋은 규칙 2개씩
- 정밀도는 낮게 나오지만(13%) 정답셋이 **시연 장면 충돌만** 적어 둬서다. 나머지는 틀린 판정이 아니라 정답셋에 없는 판정 — 사람이 검토해 정답셋에 넣어야 정밀도를 말할 수 있다
- 규모: 작업 100개 164ms · 500개 4.4초 · 1,000개 17.9초 (작업 수의 제곱으로 늘어남 — 개선 후보)

### 작업표준서 매칭 (F8) — `samples/eval_sop.py` (임베딩 없이 규칙 점수)

| 지표 | 값 |
|---|---|
| 1순위 정확도(엄격) | **84.6%** (11/13) · 함께 맞는 공통 표준서까지 92.3% |
| 필수 단계 누락 검출 | 2/2 검출, 잘못 검출 0 (배관O 「작업 전 가스 측정」 누락 ○) |
| 매칭 시간 | 계획서당 2~3ms |

정답 표준서는 새로 만든 `samples/answers_sop.json` (작업별 이유 기록). 못 맞힌 2건: 기준 ID·위험 유형이 없는 「장입 구동부 시운전」, P30 한계의 비계 해체.

### TBM 전달 확인 (F7) — `samples/eval_tbm.py`

| 입력 | 항목 판정 | 일부러 뺀 항목 | 잘못 「빠짐」 | 시간 |
|---|---|---|---|---|
| 대본 글 | 4/4 | 찾음 | 0 | 1ms 미만 |
| 음성 → 글 (whisper large-v3-turbo, 81초 음성) | 3/4 | 찾음 | 1 | 받아쓰기 90.6초 |

- 받아쓰기 글자 오류율(CER) **9.0%**. 「가연성 가스 농도 10퍼센트 미만」 구절이 빠져 가스 측정 항목을 「빠짐」으로 잘못 판정 → **음성 인식 오류가 판정에 주는 영향**을 보여 주는 숫자
- 주의: 항목 판정은 실제로는 LLM(`llm/tbm_check.py`)이 한다. 키가 없어 지금 숫자는 **키워드 대조로 대신한 값**이다. 키를 넣고 다시 잰다

## 실험 3. 작업표준서 매칭 (F8)

- 작업마다 정답 표준서를 정답셋에 추가 → 1순위 정확도, 3순위 안 포함률
- 필수 단계 누락 탐지: 배관O 계획서의 「작업 전 가스 측정」 누락을 찾는지 (정답 있음)

## 실험 4. TBM 전달 확인 (F7)

- 음성 → 글: `samples/tbm/` 81초 합성 음성, 대본 대비 글자 오류율(CER), 처리 시간
- 항목 판정: 공유 4항목 중 빠진 1건(`expected_missing`)을 찾는지, 잘못 빠졌다고 한 항목 수
- 조건 비교(선택): 대본 글을 바로 넣었을 때 vs 음성 인식 글을 넣었을 때 → 음성 인식 오류의 영향

## 실험 5. 전체 걸린 시간 (종단)

- 계획서 업로드(`POST /api/plans` 경로) → 충돌 판정 결과까지 API 응답 시간, 5건 합계
- **비교 기준(사람)**: 팀원 2명이 같은 5건을 기준 일정과 직접 대조해 충돌을 찾는 시간과 찾은 수를 실제로 잰다. 추정치를 쓰지 않는다

## 돌리는 명령 (모두 `app/backend`에서)

| 측정 | 명령 |
|---|---|
| 표본 다시 만들기 | `uv run python ../samples/make_variants.py` (통일 양식 5건 + 변형 20건, 고정 시드) |
| 추출 ①~④ | `uv run python ../samples/accuracy.py --mode <llm-raw\|llm\|rules\|auto> [--samples ../samples/variants] --repeat 3 --json 결과.json` |
| 추출 ⑤ | `uv run python ../samples/accuracy.py --samples ../samples/uniform --repeat 3` |
| 판정 | `uv run python ../samples/eval_conflicts.py [--from-extraction rules\|llm\|auto\|llm-raw] [--scale 100,500,1000]` |
| 표준서 | `uv run python ../samples/eval_sop.py` |
| TBM | `uv run python ../samples/eval_tbm.py [--no-stt]` |

- 추출은 API를 거치지 않고 `extract_plan`을 직접 불러서 서버 캐시가 끼지 않는다. Claude 쪽 시스템 프롬프트 캐시는 켜져 있으니 시간·비용은 「첫 건」과 「둘째 건부터」를 나눠 적는다(`accuracy.py`가 캐시 읽기·쓰기 토큰을 따로 출력)
- LLM 토큰은 Claude 제공자만 기록된다 (LM Studio는 시간만)

## 남은 일

1. `.env`에 `ANTHROPIC_API_KEY` 넣고 ①②④를 기본·변형 표본에서 3회씩 → 위 표 채우기
2. (선택) LM Studio로 ⑥
3. 판정 정답셋 보강: 지금 정답 외 판정을 사람이 검토해 정밀도 계산 가능하게
4. 실험 5: 팀원 2명이 5건을 직접 대조한 시간 재기
5. 규칙 보강 후보(보고서에 「개선 전/후」로 쓸 수 있음): 두 자리 연도 날짜, 「기준 일정 ID」 칸 읽기, 판정 속도(작업 1,000개 17.9초)
