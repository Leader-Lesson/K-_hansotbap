## 1. 개요

### 1.1 프로젝트 소개
각 협력사의 작업계획서는 하나씩 보면 정상이지만, 겹치면 위험하다. 우리는 양식이 제각각인 협력사 계획서를 AI로 구조화하고, 규칙으로 계획 간 충돌을 미리 찾아 원청이 조정하고 협력사에 공유하는 시스템을 만든다. 기준 현장은 포스코 광양 2고로 개수(2026-11-12 ~ 2027-03-23, 132일)이며, 같은 구조는 여러 협력사가 한 공간에 들어오는 모든 정기보수·셧다운 공사에 적용된다.

## 2. 문제 정의

### 2.1 해결하려는 문제
**핵심 메시지: 소통의 부재가 사고를 만든다.**

협력사 작업계획은 업체마다 따로 쓰고 따로 승인되기 때문에, 계획끼리 겹치는 위험을 미리 대조하는 사람이 없다.

| 겹침 형태 | 예 |
|---|---|
| 같은 시간·같은 구역 | 3층 용단 작업 옆에서 다른 업체가 보온재(가연물) 교체 |
| 위아래 | 노정 장입설비 설치 바로 아래에서 노저 축조 |
| 작업 순서 | 축조가 끝나기 전에 다른 업체가 가스 배관 연결 |

### 2.2 문제의 근거
- 2020년 사고사망자 5명 중 1명(178명)은 혼재작업 중이었다 (고용노동부 도급사업 매뉴얼, 2022)
  - 출처: 매일노동뉴스 「산재 사고사망자 20% '혼재작업'하다 숨졌다」, 전체 사망자 882명: 고용노동부 「'20년 산업재해 사고사망 통계」
- 최근 5년 철강 사망 75명 중 21%가 원·하청 정보공유 부재 속 동시작업에서 발생 (고용노동부, 2021)
  - 출처: 세이프티퍼스트닷뉴스 「철강산업 지난 5년간 사망사고 75명 발생」 (동시작업 사망 16명 = 21%)
- 2013년 현대제철 당진 전로 보수: 내화벽돌 교체가 끝나기 전 다른 협력업체가 아르곤 배관을 연결해 5명 사망. 숨진 노동자들은 배관 연결 사실을 몰랐다.
  - 출처: 뉴데일리 「사고 원인 아르곤 가스 누출로 밝혀져」(경찰 수사 결과), 주간경향 「잇단 사망사고는 '3고로 공기단축' 때문」
- Piper Alpha(1988, 167명): 작업허가가 위치가 아니라 직종별로 철해져 같은 설비의 충돌을 아무도 보지 못했다.
  - 출처: The Chemical Engineer 「Piper Alpha: The Disaster in Detail」, IChemE 「Cullen Report」
- 법: 산안법 제64조 제1항 7·8호(원청의 혼재작업 확인·조정 의무), 제65조(위험 작업 도급 시 안전·보건 정보 문서 제공)
  - 출처: 국가법령정보센터 제64조, 제65조

### 2.3 기존 해결책과 한계
| 기존 서비스/방법 | 장점 | 한계 |
|---|---|---|

## 3. 타깃 사용자

### 3.1 주요 사용자
- 원청 안전·공정 담당자 (예: 포스코 총괄 담당자): 전체 계획을 보고 충돌을 조정한다.
- 협력사 현장 책임자: 계획서를 제출하고, 자기 작업과 관련된 충돌·표준서·공지를 받는다.
- 현장 작업자: TBM에서 위험 시간대와 조정 내용을 전달받는다.

### 3.2 페르소나
| | 페르소나 1: 원청 공정 담당자 / 40대 | 페르소나 2: 배관 협력사 현장 소장 / 50대 |
|---|---|---|
| 상황 | 개수 기간 동안 협력사 수십 곳의 계획서를 승인해야 한다. | 일정이 당겨져 가스 배관 연결을 앞당기려 한다. |
| 불편한 점 | 양식이 다 달라서 업체 간 겹침을 머릿속으로 대조한다. 계획이 바뀌면 다시 다 봐야 한다. | 같은 구역에서 다른 업체가 무엇을 하는지 모른다. |
| 원하는 것 | 겹치는 작업만 근거와 함께 먼저 보고 싶다. | 내 작업과 겹치는 작업, 지켜야 할 표준서만 알고 싶다. |

### 3.3 사용 시나리오
배관 협력사가 수정한 계획서를 평소 쓰던 엑셀 그대로 올린다. 시스템이 이를 구조화하자 노흉 축조가 끝나기 전에 질소 라인을 연결하는 순서 위반이 뜬다. 원청 담당자는 근거 조문과 함께 "축조 완료·인원 철수 확인 후 연결" 조정안을 적용하고, 배관·축조 협력사 화면에는 위험 시간대 공지가 뜬다. 다음 날 아침 TBM 녹음으로 이 내용이 작업자에게 전달됐는지 확인한다.

## 4. 해결 방안

### 4.1 서비스 컨셉
협력사가 이미 내는 계획서를 그대로 받아 AI가 구조화하고, 규칙 엔진이 겹침을 판정하면 원청이 조정해 관련 협력사에 공유한다.

1. 제출: 협력사가 지금 쓰는 양식 그대로 작업계획서를 올린다. 변경 시에도 말이 아니라 수정한 계획서로 다시 제출한다.
2. 구조화: AI가 업체·작업·기간·위치·작업 유형·선행 조건을 뽑아 표로 만든다.
3. 표준서 매칭: 작업마다 원청 작업표준서를 찾아 붙이고, 필수 단계 누락을 본다.
4. 판정: 규칙 엔진이 같은 시간·구역, 위아래, 화기×가스, 순서 위반을 찾는다.
5. 조정: 원청 담당자가 조정안을 보고 일정이나 순서를 바꾼다.
6. 위험 시간대 예보: 판정 결과를 시간대별로 모아 공지한다.
7. 공유: 관련 협력사는 자기 작업과 겹친 결과만 받는다.
8. 전달 확인: TBM 음성으로 작업자 전달 여부를 확인한다.
9. 기록: 조정 결정과 책임자가 남아 제64조 이행 기록이 된다. 계획이 바뀌면 2번부터 다시 돈다.

- 작업계획서(협력사 작성): 작업을 어떤 순서로 언제 할지
- 작업표준서(원청 보유): 각 작업을 어떤 방법·절차로 할지 (소요 시간, 가스관·천장·바닥 등 세부 사항)

### 4.2 핵심 가치 (설계 원칙)
- 서류를 늘리지 않는다: 새 양식을 강제하지 않고 지금 내는 계획서를 입력으로 쓴다.
- 판정은 규칙, AI는 읽기와 설명: 충돌 판정은 법·지침 근거가 있는 규칙이 하고, LLM은 추출·위치 매핑·사유 설명·조정안 문장만 맡는다.
- 결정은 사람이 한다: 시스템은 작업을 승인하거나 중지하지 않는다.
- 근거를 항상 붙인다: 모든 판정에 규칙 ID, 법 조문, 원문 문장을 표시한다.

### 4.3 차별점
| 구분 | 기존 방식 | 이 프로젝트 |
|---|---|---|
| 보는 대상 | 사람·작업개소 현황 | 작업 간 관계(위아래, 순서, 같은 시간의 화기와 가스) |
| 시간 범위 | 오늘 | 공정 전체(개수 132일) |
| 입력 | 정형 데이터 등록 | 이미 내는 계획서(HWPX·엑셀·PDF) 그대로 |
| 결과 | 현황 표시 | 충돌 판정 + 표준서 매칭 + 근거 조문 + 조정안 + 위험 시간대 + 권한별 공유 + 전달 확인 + 이행 기록 |

기존 시스템을 대체하지 않고 그 위에 얹는 층이다. 시스템이 있는 원청은 데이터를 연동하고, 없는 원청은 계획서를 업로드한다.

| 필수 | F8 작업표준서 매칭 | 공유 폴더의 표준서를 계획서 작업마다 매칭, 매칭 이유·신뢰도 표시, 필수 단계 누락은 F2 '결함'으로 | AI + 규칙 | O |
| 필수 | F9 위험 시간대 예보 | 판정 결과를 시간대별로 모아 협력사·공정·구역별 위험 시간대를 뽑고 근거와 함께 공지 | 규칙 + AI | O |
| 연결 | F6 챗봇 | "내일 노정에서 누가 무슨 작업?", "내 작업과 겹치는 작업은?" 등 질의. 권한 범위 안에서 답하고 근거 표시 | AI + 조회 | O |
| 연결 | F7 TBM 전달 확인 | TBM 음성 전사 → 공유된 충돌·조정·위험 시간대가 전달됐는지 LLM이 확인, 빠진 항목 알림 | AI | O |
| 선택 | 동선 시뮬레이션 | 시간대별 작업자·작업 차량 동선 표시 (작업표준서 기반) | — | X (여유 시) |

**권한 구조**
- 원청: 전체 열람
- 협력사: 자기 업체 데이터만. 다른 업체 데이터는 접근 불가
- 공유 범위: 원청이 공유하기로 한 것만 — 인접 위치 작업, 위험 요소, 작업 인계 조건(예: "여기까지 완료돼야 다음 업체 착수")

**하지 않을 것:** 실시간 위치 추적, 전자 작업허가 시스템 전체 구축, 계획과 실제 작업의 차이 감지, 작업 승인·중지 자동화

### 5.2 MVP 범위
11월 9일 24시까지 F1~F9를 모두 구현한다. 시연의 중심은 F1→F2→F3→F4이고, F5~F9는 그 흐름에 이어 붙인다. 시간이 부족하면 F6·F7은 단일 질의/단일 녹음 파일 데모로 줄인다.

### 5.3 사용자 흐름 (User Flow)
```
[협력사 계획서 업로드] → [F1 구조화·확인] → [F8 표준서 매칭] → [F2 충돌 판정]
  → [F3 간트·3D·단면도 표시] → [F4 원청 조정안 적용·재판정] → [F9 위험 시간대 공지]
  → [F5 협력사별 공유·기록] → [F6 챗봇 조회] → [F7 TBM 전달 확인]
  ↺ 계획 변경 시 수정 계획서 재제출 → F1부터 다시
```

### 7.1 기술 스택
| 구분 | 기술 | 비고 |
|---|---|---|

| 백엔드 | Python + FastAPI | |
| DB | SQLite | 설치 없이 파일 하나 |
| LLM (클라우드) | Claude API | 구조화 출력, 도구 호출 |
| LLM (로컬) | LM Studio (OpenAI 호환 로컬 API) | 연결·임베딩 동작 확인 완료 |
| 임베딩 | LM Studio 임베딩 모델 | 작업표준서 검색 |
| 벡터 검색 | FAISS 또는 Chroma | |
| 음성인식 | Whisper large-v3-turbo / large-v3 (로컬) | turbo = 속도, large-v3 = 정확도, 설정으로 선택 |

**기능별 기술**
| 기능 | 처리 | 기술 |
|---|---|---|
| F1 계획서 구조화 | 파일 → 텍스트 → JSON(업체·작업·기간·작업 시간·위치·작업 유형·선행 조건) | 파서 + Claude |
| F2 충돌 판정 | 시간 겹침 + 구역·위아래 관계 + 규칙 30개 | Python 규칙 엔진 |
| F3 시각화 | 3D 고로 + 간트 | three.js, vis-timeline |
| F4 조정안·재대조 | 조정안 문장 생성, 적용 후 재판정 | Claude + 규칙 엔진 |
| F5 공유·이력 | 역할별 필터, 조정 결정·책임자 기록 | FastAPI + SQLite |
| F6 챗봇 | 질문 → 조회 함수 호출 → 근거 붙은 답 | Claude 도구 호출 |
| F7 TBM 전달 확인 | 녹음 → 텍스트 → 공유 내용 언급 여부 판단 | Whisper + Claude |
| F8 작업표준서 매칭 | 표준서 → 임베딩 → 작업별 매칭, 필수 단계 누락 판정 | LM Studio 임베딩 + FAISS/Chroma + 규칙 |
| F9 위험 시간대 예보 | 판정 결과 시간대별 집계·점수화 → 표시·공지 | pandas + 규칙 + Claude |

**구조 원칙**
- Claude와 LM Studio를 같은 인터페이스(LLMProvider) 뒤에 두고 설정으로 전환한다 → 사내 데이터를 외부로 못 보내는 현장은 로컬 모델로 운영 가능
- 판정(F2 충돌, F8 누락, F9 점수)은 규칙 코드로 하고 pytest로 검증한다. LLM은 추출·설명·문장 생성만 맡는다
- 모든 판정에 근거(규칙 ID, 법 조문, 원문 문장)를 붙인다
- 챗봇은 SQL을 직접 실행하지 않고 조회 함수를 도구로 쓴다
- 화면에 "합성 데이터"를 표시하고, 협력사명은 가상으로 쓴다
- API 키는 환경변수로만 관리한다

### 7.2 시스템 구조도
```
[작업계획서 HWPX·엑셀·PDF]      [작업표준서 폴더]      [TBM 녹음]
            │                         │                  │
            ▼                         ▼                  ▼
[FastAPI]
  ├─ parsers   PDF·엑셀·HWPX → 텍스트
  ├─ llm       LLMProvider: Claude | LM Studio (추출·설명만, 화면은 다루지 않음)
  ├─ rules     F2 판정, F8 누락, F9 점수
  ├─ search    F8 임베딩 인덱스(FAISS/Chroma)
  ├─ stt       F7 Whisper large-v3-turbo / large-v3
  └─ db        SQLite (업체·작업·기간·구역·인원·판정 결과)
            │ REST
            ▼
[React 프론트 — 표시 전용] 원청 화면 / 협력사 화면 (역할 선택)
  ├─ 시간표형 간트 (vis-timeline)
  ├─ 고로 3D·2D 도면 (three.js)
  └─ 챗봇 UI
```
- 판정은 계획서가 제출되는 순간 실행한다. 실시간 추적이 아니라 제출 시점 대조다.
- 동시에 제출되면 먼저 들어온 계획을 기준으로 대조한다.
- 판정이 끝나면 화면을 한 번 강제 새로고침해 반영한다.

- 결정은 결정사항 메모에, 진행 상황은 시간별 작업 로그에 바로 남긴다. 말로만 정한 건 정하지 않은 것으로 본다.
- 막히면 30분 안에 공유한다.

## 10. 기대 효과와 확장성

### 10.1 기대 효과
- 원청: 계획서 검토·협의 준비 시간 단축, 제64조·제65조 이행 기록 확보
- 협력사: 내 작업과 겹치는 위험과 지켜야 할 표준서를 착수 전에 앎
- 사회적 측면: 소통 부재로 인한 혼재작업 사고 예방

**우리가 잴 수 있는 지표**
- 착수 전 찾아낸 충돌 건수와 유형
- 위험 시간대 공지 후 분산·조정된 작업 수
- 계획 변경 뒤 재대조까지 걸린 시간 (수작업 대비)
- 계획서 추출 정확도 (합성 정답셋 기준)

**참고 사례** (협업 구조 전반의 근거, 대부분 대조군 없는 전후 비교)
| 사례 | 결과 |
|---|---|
| Dow 화학단지: 원청+협력사 85곳 안전 연합 | 협력사 재해율 3.43 → 0.20 |
| ArcelorMittal 멕시코: 작업허가 전 위험성평가 의무화 | 휴업재해율 2.6 → 0.5, 사망 3 → 0 |
| 국내 대·중소기업 상생협력 1만여 곳 | 사고사망만인율 0.17 → 0.07 |
| 미국 병원 공사: 착공 전 공종 통합 조율 | 현장 간섭 질의 200~300건 → 2건 |

### 10.2 수익 모델
- 원청 대상 SaaS(현장·공사 단위 과금), 기존 전자 작업허가 시스템과의 연동 모듈

### 10.3 향후 확장 계획
- 화학·발전·제지 정기보수, 반도체 라인 개조, 건설 현장 — 구역 정의와 규칙표만 바꿔 적용
- 작업표준서 기반 작업자·차량 동선 시뮬레이션
- 휴대폰 등 여러 기기 지원 (현재 TBM은 모니터 앞에서 진행)
