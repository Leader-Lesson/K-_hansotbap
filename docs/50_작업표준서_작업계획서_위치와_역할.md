# 작업표준서·작업계획서 — 어디에 있고 누가 읽는가

> 작성 2026-11-09. 두 문서가 어디 있는지, 시스템이 어떤 파일을 읽는지, 사람이 보는 문서는 어떤 형식인지 정리한다. 모두 **합성 데이터**이며 협력사명은 가상(`가상-…`)이다.

## 1. 한눈에

| 문서 | 누가 만드나 | 사람이 보는 파일 | 시스템이 읽는 파일 | 위치 |
|---|---|---|---|---|
| 작업표준서 (SOP) | 원청 | **PDF** `app/backend/data/sop/pdf/` | 마크다운 + `index.csv` (같은 폴더) | `app/backend/data/sop/` |
| 작업계획서 | 협력사 (양식 제각각) | **PDF · Word · HWPX · 엑셀** 그대로 | 업로드한 파일 자체 (F1 파서가 읽음) | `app/samples/` (시연용 합성 계획서) |

- 표준서 PDF는 마크다운에서 `make_sop_pdf.py`로 만든다. 사람이 보는 문서와 판정에 쓰는 문서가 어긋나지 않게 **원본은 하나(마크다운)** 두고 PDF는 변환한다.
- 계획서는 협력사가 내는 파일이 그대로 원본이다. 시스템은 양식을 강제하지 않고, 업로드된 파일을 파서(PDF·엑셀·HWPX)가 읽고 머리글을 알아보면 규칙으로, 모르면 LLM으로 구조화한다(F1).

## 2. 작업표준서 — `app/backend/data/sop/`

| 파일 | 역할 |
|---|---|
| `SOP-01~04_*.md` | 공통 표준서 4종(화기·밀폐공간·중량물 인양·가스 배관). 작업 유형별 |
| `SOP-P01~P37_*.md` | 작업별 표준서 37종. 기준 일정(`gy2bf_wbs.csv`) 작업 하나에 하나 |
| `index.csv` | 표준서 ID·제목·파일·적용 작업 유형·적용 작업(WBS)·필수 단계·출처·작업명 낱말. **F8 매칭이 읽는 표** |
| `pdf/*.pdf` | 사람이 보는 표준서. 마크다운에서 변환 |
| `make_sop_pdf.py` | 마크다운 → PDF 변환기 (`uv run python data/sop/make_sop_pdf.py`) |
| `README.md` | 표준서 목록·파일 규칙 |

시스템이 읽는 부분(이 부분을 고치면 코드 수정 없이 판정 기준이 바뀐다):

- `## 필수 단계` 번호 목록 ↔ `index.csv` 필수 단계 열 (같아야 한다)
- `## 판정에 쓰는 기준` 안의 "계획서 절차에 N·M 단계가 없으면 …" 문장 → 핵심 단계(빠지면 F2 결함)
- `## 작업 금지·출입 제한` 절(있어야 한다). 지금은 사람이 읽는 글이고, 3D 출입 금지 표지는 F2 금지 판정에서 만든다

매칭과 판정은 규칙이다(`search/sop_match.py`, `rules/sop_steps.py`). LLM은 표준서를 읽지 않는다. 임베딩은 설정했을 때만 순위·이유를 보강한다.

## 3. 작업계획서 — `app/samples/`

| 파일 | 역할 |
|---|---|
| `가상-*.pdf / .docx / .hwpx / .xlsx` | 합성 협력사 계획서 8건(5건 기존 + 양중C PDF·기계E Word·축로L HWPX 예시). 협력사마다 양식이 다르다 |
| `answers/<파일명>.json` | 정답셋: 업체·작업·구역·기간·인원·작업 유형·선행 작업·기준 일정 ID·내야 하는 충돌. `accuracy.py`가 추출 정확도를 잰다 |
| `make_samples.py` | 계획서·정답셋 생성 스크립트 (`cd app/backend && uv run python ../samples/make_samples.py`) |
| `README.md` | 계획서 목록·양식·시연에서 내는 충돌 |

계획서에 **있어야 하는 것**(3D·판정에 쓰는 정보):

| 항목 | 쓰는 곳 | 비고 |
|---|---|---|
| 업체명 | 권한 필터, 충돌 상대 표시 | 문서 머리나 표 열 |
| 작업명 | 기준 일정 매칭, 표준서 매칭(작업명 낱말) | |
| 위치 (구역 + 구역 안 세부 위치·방위) | 3D 구역 배치, 같은 시간·구역/위아래 판정 | 세부 위치(북측·풍구 12~16번 등)가 있어야 3D가 구역 안 방위까지 보여 준다 |
| 기간·작업 시간·주야간 | 간트, 3D 시간 슬라이더, 겹침 판정 | 07~19시 30분 칸 기준 |
| 투입 인원 | 3D 작업자 수, 상황판 인원 | 지금은 추출만 되고 저장 안 됨(스키마 보강 예정). 정답셋 `headcount`에는 있다 |
| 투입 장비 | 3D 장비 배치, 크레인·차량 규칙(R18~R21) | 지금은 읽지 않음(스키마 보강 예정). 정답셋 `equipment`에는 있다 |
| 위험작업·필요 허가 | 작업 유형(화기·밀폐·고소·중량물·가스) | |
| 선행 조건 | 순서 위반(R08) | "P22 완료 후"처럼 작업명이나 ID |
| 작업 절차 | 표준서 필수 단계 확인(F8) | 단계 낱말이 한 줄에 있어야 "기재"로 본다 |
| 비용·자재·보호구·비상연락 | 3D에는 안 쓰지만 실제 계획서에 있는 항목 | 사람이 보는 문서로서의 완성도 |

지원 형식: PDF(PyMuPDF), 엑셀(openpyxl), HWPX(XML), **Word(.docx, python-docx — 2026-11-09 추가 `parsers/docx.py`)**. 업체명은 문서 머리의 "업체명: X" 또는 머리 표의 "업체명 | X" 칸에서 읽는다.
